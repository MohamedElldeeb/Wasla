**Score model** (per campaign, in the database, tested): signed weights −100..100. `score = round(100 · Σ(wᵢ·nᵢ − min(wᵢ,0)) / Σ|wᵢ|)` over the signals actually collected for that lead; unknown signals are ignored. Positive weight rewards the HIGH state of a signal, negative rewards the LOW state, so "no website" is good for one offer and neutral/bad for another. Top 3 favourable contributions become short Arabic reasons.

## 2. Architecture state
Presentation (Next.js, server actions) → `create_job` RPC (reserve) → signed webhook → n8n → Supabase (service role) → `settle_job`. The UI only reads state (RLS) and subscribes to `jobs`. Ingestion is connector-shaped: `ingest_leads` takes the normalized lead shape (place-level and person-level columns), so Apollo/Instagram/etc. are new adapters in front of the same function.

## 4. Risks, shortcuts and technical debt
1. **Apify MCP was not available in this session.** I used the Apify REST API directly for the capped sample runs (`scripts/apify-sample.mjs`, 8 places and 20 reviews). Samples are in `docs/samples/`. The product itself calls Apify from n8n, as required.
2. **Apify run-sync window is 300 s**, so Phase 2 caps a campaign at **100 leads** (`defaults.maxResultsCap`). Bigger runs need async runs + polling (Phase 3/4).
3. **`business_age` is an estimate.** Only the 10 newest reviews are fetched, so true age cannot be read. The workflow estimates age from review velocity (`raw.method = velocity_estimate`) and a place with all reviews visible uses the real oldest date. For busy older places it correctly says "established", but treat it as a rough signal.
4. Many reviews have no text, so `review_insights` is only produced when ≥ 3 reviews have text (1 of 4 leads in the test).
5. **Planner quality:** it sometimes returns a few keywords that describe the seller's own trade (competitors) next to good prospect keywords. The prompt now says prospects only, and the draft is always editable, but a "check your keywords" hint in the UI would help.
6. **Message validation rejects, it does not retry:** invalid output (word count, links) is dropped and not charged; running "اكتب الرسايل" again fills the gaps. Extra emojis are now stripped instead of rejected. One automatic retry is a cheap Phase 4 improvement.
7. **Model config:** `OPENROUTER_MODEL` / `OPENROUTER_FALLBACK_MODELS` are read by the Next server and sent in each webhook payload (n8n cannot read your env). Changing them needs a restart/redeploy of the app, not a code change. Per-campaign override is supported in `llm_model_override` but has no UI yet.
8. **n8n stores execution data** (including lead data) by default. Set execution pruning / "do not save successful executions" on the instance before real use (PDPL).
9. If an n8n node crashes after the claim, the job stays `running` with credits reserved. The WF5 housekeeping job (Phase 4) releases stale reservations; until then an admin can call `settle_job`.
10. Next.js 16 `cacheComponents` is switched **off** in `next.config.ts` (every page here is per-user dynamic). Revisit when adopting partial prefetching.
11. UI strings live in `lib/i18n/ar.ts` (typed). A few labels in the wizard (weight explanation) are still inline Arabic; move them in Phase 4.
12. Hand-written row types in `lib/types.ts` instead of generated Supabase types (kept the diff small). Regenerate with the MCP when the schema stabilises.
13. Realtime is wired but polling (4 s) is what I observed driving the UI in tests; I did not separately prove websocket delivery.
14. Dark mode tokens exist; there is no toggle yet.
15. Supabase **leaked-password protection is off** (dashboard setting, flagged by the advisor). The default Supabase email sender is rate-limited (hit during testing), so signup emails need your own SMTP before real onboarding. `email_confirm` is required, as the spec says.
16. Onboarding is reachable by a user who already has an organization (limit: 3 owned orgs, enforced in the database).
17. I accidentally triggered one signup confirmation email to a throw-away address while probing the auth endpoint; that user was deleted immediately. All other test accounts use `@wasla.test` and were created confirmed through the admin API.
